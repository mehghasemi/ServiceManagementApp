# کار روزمره هم‌زمان با توسعه

## راه‌اندازی مستقل از Codex — ۱۸ اکتبر ۲۰۲۶

دو وظیفه Windows Task Scheduler با نام‌های ServiceManagementApp-stable و ServiceManagementApp-development نصب شده‌اند. نسخه اصلی روی 8769 از release ثابت و دیتابیس preview.sqlite3 و توسعه روی 8768 از کد جاری و development.sqlite3 اجرا می‌شود. نصب اولیه: `powershell -ExecutionPolicy Bypass -File install-runtime-tasks.ps1 -Start`. نصب مجدد روی وظیفه موجود عمداً رد می‌شود؛ انتشار جدید باید جداگانه بررسی و فعال شود. prepare دیگر روی مسیر پین‌شده این وظیفه اثر ندارد.

وظیفه‌ها تحت حساب فعلی ویندوز، مستقل از فرایند Codex، با ورود کاربر شروع می‌شوند، محدودیت زمان اجرا ندارند و پس از خروج ناموفق هر یک دقیقه تا ۹۹۹ بار تلاش مجدد دارند. پیکربندی و نسخه ثابت راه‌انداز در private/operations و لاگ‌ها در private/*-task.log و *.error قرار دارند. اجرای دستی start-stable و start-development در زمان فعال‌بودن وظیفه‌ها لازم نیست.

این روش سرویس Windows بدون نشست کاربر نیست: قفل صفحه مانعی ندارد، ولی خروج از حساب، خاموشی یا Sleep دسترسی را قطع می‌کند. اجرای پیش از ورود نیازمند حساب سرویس سازمانی با دسترسی CRM و پیکربندی IT است؛ LocalSystem جایگزین هویت CRM نشده است. در این مرحله فایروال یا دسترسی LAN تغییر نکرده است. هر دو نشانی محلی HTTP 200 و وضعیت Running زمان‌بند بررسی شد؛ خروج از Codex، راه‌اندازی مجدد ویندوز و بازیابی پس از crash هنوز آزمون عملی نشده‌اند.

کدِ در حال ویرایش نباید منبع فایل‌های برنامه کاری باشد. runtime.py prepare یک کپی مستقل از کد، قالب و static در private/releases می‌سازد؛ دیتابیس و تنظیمات محرمانه را داخل release کپی نمی‌کند. هر release تازه پوشه مستقل دارد و قبلی بازنویسی نمی‌شود. اشاره‌گر release-next فقط اجرای بعدی را تعیین می‌کند و برنامه در حال اجرا را تغییر نمی‌دهد.

- ساخت نسخه: `.venv\Scripts\python.exe runtime.py prepare`
- کار روزمره محلی: `start-stable.ps1`، نشانی http://127.0.0.1:8769 با دیتابیس کاری قبلی.
- اولین آماده‌سازی توسعه از یک کپی سازگار SQLite: `.venv\Scripts\python.exe runtime.py development --copy-current`، نشانی http://127.0.0.1:8768.
- اجراهای بعد توسعه: `start-development.ps1`. داده و اقدام‌ها در private/development.sqlite3 مستقل‌اند. گزینه کپی روی دیتابیس موجود رد می‌شود تا کار توسعه بازنویسی نشود.
- اجرای شبکه از release مستقل: `.venv\Scripts\python.exe runtime.py stable --network` روی پورت 8766. اگر اجرای قدیمی روی پورت فعال باشد، خودکار متوقف نمی‌شود؛ انتقال پورت نیازمند زمان هماهنگ و پایان job جاری است.

کد توسعه و داده آزمایش به محیط کاری خودکار منتقل نمی‌شوند. هیچ‌یک از راه‌اندازها فرایند جاری را برای شما نمی‌بندند. هر دو محیط CRM را فقط می‌خوانند. داده توسعه کپی واقعی و محرمانه است و فقط در private می‌ماند؛ برای تست‌های خودکار همچنان از داده ساختگی استفاده شود.

این طراحی مانع اختلال ناشی از ویرایش روزمره می‌شود؛ انتشار نسخه یا تغییر schema بدون توقف را تضمین نمی‌کند. برای ارتقای نسخه، تست، پشتیبان سازگار SQLite، بررسی migration و زمان تعویض فرایند لازم است. ارتقای وابستگی venv مشترک نیز باید خارج از زمان کار انجام شود؛ انتشار با محیط وابستگی مستقل و reverse proxy مرحله بعد است. نشانی‌های قدیمی 8765 و اجرای مستقیم run_lan.py از پوشه توسعه، همچنان روش قدیمی‌اند.

اعتبارسنجی 0.6.0: ۶۰ آزمون موفق از جمله استقلال release و عدم تأثیر نوشتن در دیتابیس توسعه بر دیتابیس اصلی. بررسی migration تغییری نشان نداد و نحو JavaScript و diff بدون خطا بودند. دریافت واقعی View در دیتابیس توسعه موفق شد؛ دیتابیس اصلی با این دریافت تغییر نکرد. سه مهارت تخصصی در پوشه مهارت‌های Codex ساخته و با quick_validate اعتبارسنجی شدند.

آزمون اجرایی: نسخه پایدار روی 8767 و توسعه روی 8768 هم‌زمان بالا آمدند، بدون توقف پورت‌های قبلی. دکمه بازخوانی نسخه پایدار از مرورگر اجرا شد و دریافت موفق جدید در همان دیتابیس کاری ثبت شد. نمایش ۳۹۰ پیکسل بدون سرریز افقی سند، راهنمای تازگی و بازگشت فوکوس با Escape بررسی شدند. تصویر فقط در private نگهداری شد. انتقال اجرای شبکه قدیمی به release مستقل هنوز انجام نشده و باید در زمان هماهنگ صورت گیرد.

نسخه نهایی این نوبت با صف مستقل موارد بدون برنامه روی 8769 ارائه می‌شود؛ نسخه قبلی 8767 متوقف نشده است. راه‌انداز توسعه از اجرای بعدی بازبارگذاری خودکار کد دارد؛ این رفتار در نسخه پایدار غیرفعال است.


رفع خطای اتصال 0.6.3: اجرای محصور ابزار ممکن است درخواست PowerShell با هویت ویندوز را با ReceiveFailure متوقف کند. در بررسی ۲۵ مهر، درخواست WhoAmI در اجرای عادی کاربر HTTP 200 داد و پس از راه‌اندازی مجدد فقط محیط توسعه، دریافت شماره ۱۱ با ۱۰۲۶ کیس موفق شد. برای اجرای روزمره توسعه از start-development.ps1 در نشست ویندوز مجاز استفاده شود. خطای بدون پاسخ HTTP دیگر با عنوان نادرست HTTP 0 نمایش داده نمی‌شود؛ پیام بر اساس نوع خطای شبکه است و رمز یا متن خام استثنا نمایش داده نمی‌شود.

انتشار 0.6.6: پس از ۶۲ آزمون موفق، بررسی نبود migration جدید و نبود job فعال، پشتیبان SQLite گرفته شد و وظیفه stable به release مستقل 20261018T105443525539 منتقل شد. فرایند شنونده 8769 از همین مسیر و سلامت HTTP 200 تأیید شد. دیتابیس توسعه جایگزین کاری نشد. بررسی تصویری به علت رد ابزار مرورگر انجام نشد.

اصلاح راه‌انداز ۱۸ اکتبر: Start-Process فرایندهای قدیمی را زنده گذاشته بود و SO_REUSEADDR در ویندوز باعث چند شنونده هم‌پورت شده بود. اجرای مستقیم managed_runtime.py در Task Scheduler و SO_EXCLUSIVEADDRUSE جایگزین شد. autoreload در اجرای مدیریت‌شده غیرفعال است؛ تغییر کد توسعه نیازمند Restart وظیفه development است. آزمون توقف توسعه: شنونده توسعه صفر شد و PID نسخه اصلی ثابت ماند؛ توسعه دوباره راه‌اندازی شد. نسخه اصلی همچنان release 20261018T110547512456 است.

بررسی بعدی کد خروج 0xC000013A (خروج کنسول) را نشان داد؛ وظیفه‌ها به pythonw.exe بدون کنسول منتقل شدند. آزمون قبلی پایداری طولانی‌مدت محسوب نمی‌شود.
