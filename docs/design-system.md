# سیستم طراحی همراه خدمات

این سند قرارداد طراحی برای توسعه رابط موجود است؛ ایجاد آن به معنی بازطراحی یا تأیید دسترس‌پذیری همه صفحه‌ها نیست. الزامات اصلی در [نیازهای کاربر](user-requirements.md)، وضعیت اجرا در README و جزئیات قابلیت‌ها در اسناد همان قابلیت نگهداری می‌شوند.

## ساختار واقعی و مرجع تغییر

برنامه Django با قالب سمت سرور، JavaScript ساده و CSS محلی است. نسخه وابستگی‌ها در `requirements.txt` قرار دارد. افزودن React، Tailwind، کتابخانه نمودار یا CDN برای تغییر ظاهر لازم نیست.

ترتیب stylesheetها در `templates/base.html` اکنون چنین است:

`app.css` → `workspace.css` → `grid.css` → `dashboard-design.css` → `visual-workspace.css` → `dashboard-builder.css`

قبل از تغییر، مقدار نهایی و selector غالب را در همین زنجیره بررسی کنید. تعریف اولیه یک رنگ در `app.css` الزاماً رنگ نهایی نیست. رفتار تم در `static/theme.js` و راهنمای مشترک در `static/app.js` قرار دارد. مرجع اجرای واقعی، فایل‌های موجود است؛ جدول زیر یک لایه CSS تازه ایجاد نمی‌کند.

| حوزه | مرجع | قرارداد |
|---|---|---|
| پوسته، زبان و دارایی‌ها | `templates/base.html` | `lang="fa-IR"`، `dir="rtl"`، لینک پرش، فایل‌های محلی |
| قلم و اجزای پایه | `static/app.css`، `static/fonts/` | Vazirmatn با وزن‌های محلی ۴۰۰ و ۷۰۰؛ کنترل‌ها قلم را ارث ببرند |
| زمینه و سطح | `--bg`، `--surface`، `--soft`، `--hover` | استفاده از توکن؛ مقدار روشن/تاریک از cascade موجود |
| متن و مرز | `--ink`، `--muted`، `--line` | متن فرعی همچنان خوانا؛ کنتراست باید اندازه‌گیری شود |
| اقدام و نمودار | `--accent`، `--accent-dark`، `--chart` | اقدام اصلی مشخص و پیوند قابل تشخیص |
| سری‌های نمودار | `--series-*`، `--viz-*` | رنگ دسته‌ای؛ بدون معنای ارزیابی خودکار |
| گوشه و سطح کارت | `--radius`، `--viz-radius`، `--shadow` | استفاده از اجزای موجود؛ `--viz-radius` فعلاً ۱۲ پیکسل است |
| جدول و چیدمان | `static/grid.css` و `static/grid.js` | حفظ کلیدها، مرتب‌سازی، صفحه‌بندی و ترجیح هر کاربر |
| داشبورد قابل تنظیم | `static/dashboard-builder.css` و اسکریپت‌های هم‌نام | حفظ تنظیمات، مالکیت، revision و انتشار مشترک |

## زبان بصری و ترکیب صفحه

### اندازه و رنگ مرجع

مقادیر فعلی از `dashboard-design.css` و `visual-workspace.css` استخراج شده‌اند؛ این جدول لایه CSS تازه‌ای ایجاد نمی‌کند.

| توکن | روشن | تاریک |
|---|---|---|
| `--bg` | `#f3f5fc` | `#101023` |
| `--surface` | `#ffffff` | `#1b1b35` |
| `--line` | `#dce2ef` | `#3b3e5e` |
| `--accent` | `#315ed5` | `#3569df` |
| `--viz-blue` | `#315bd8` | `#739eff` |
| `--viz-green` | `#12805b` | `#53d8a1` |
| `--viz-amber` | `#a96a00` | `#f5c458` |
| `--viz-red` | `#ce3b54` | `#ff8294` |
| `--viz-violet` | `#8151cf` | `#b797ff` |
| `--viz-cyan` | `#087d99` | `#57d6e8` |

رنگ دسته‌های مرتبط ثابت بماند. رنگ سری با وضعیت عملیاتی یکی نیست؛ قرمز، زرد و سبز فقط همراه برچسب و بر پایه داده یا معیار ذخیره‌شده معنای هشدار/موفقیت بگیرند. هدف کنتراست متن عادی ۴٫۵:۱ و متن بزرگ و اجزای تعاملی مرتبط ۳:۱ است؛ این هدف پذیرش است، نه تأیید همه ترکیب‌های فعلی.

اندازه پیشنهادی برای اجزای تازه: متن اصلی ۱۴–۱۶، فرعی حداقل ۱۲، عنوان بخش ۱۶–۲۰ و عنوان صفحه ۲۰–۲۴ پیکسل؛ وزن‌های محلی ۴۰۰ و ۷۰۰. ارتفاع خط فارسی چندخطی حدود ۱٫۶ تا ۱٫۸ و ردیف فشرده حدود ۱٫۴ باشد. فاصله‌ها بر پایه ۴ پیکسل؛ فاصله داخلی کارت معمولاً ۱۲–۱۶ و بین بخش‌ها ۱۶–۲۴. سطح قابل کلیک حداقل ۲۴×۲۴ و ترجیحاً ۴۴×۴۴ پیکسل برای لمس باشد. این‌ها استاندارد کارهای بعدی‌اند و باید با بزرگ‌نمایی بررسی شوند.

محیط کاری مدیریتی با زمینه سرمه‌ای در حالت تاریک، سطوح آرام، نمودارهای دسته‌ای و کارت‌های فشرده حفظ شود. عنوان، اقدام اصلی و وضعیت منبع پیش از جزئیات قرار بگیرند. اطلاعات پرحجم از خلاصه به نمودار، فهرست و شواهد بازشونده برسند. تزئینات نباید فضا یا توجه لازم برای تصمیم کاربر را بگیرند.

از `.page-heading`، `.panel`، `.button.primary`، `.button.secondary`، `.filters`، `.notice` و `.table-wrap` استفاده کنید؛ ابتدا کاربرد واقعی آن‌ها را در صفحه مشابه ببینید. selector جدید به قابلیت محدود شود تا صفحات دیگر ناخواسته عوض نشوند. فاصله‌های پیشنهادی برای بخش‌های جدید ۴، ۸، ۱۲، ۱۶، ۲۴ و ۳۲ پیکسل است؛ اندازه موجود اجزا بدون نیاز بازنویسی نشود. متن کاربردی برای جا دادن در کارت ریز نشود؛ شکست خط و بازچینی اولویت دارند.

برای رابط فارسی از ویژگی‌های منطقی مانند `margin-inline-start` و `padding-inline` استفاده شود. شناسه، URL و داده مختلط با `bdi` یا `dir="ltr"` ایزوله شوند. محورها و اعداد نمودار بدون بررسی معنا معکوس نشوند. تاریخ نمایشی از قالب‌بند شمسی موجود استفاده کند؛ قرارداد زمانی داده تغییر نکند.

## تعامل، فرم و راهنما

- لینک برای جابه‌جایی و دکمه برای عمل؛ نام فارسی قابل دسترس برای کنترل نمادی ضروری است.
- هر فیلد label متصل داشته باشد؛ خطا کنار فیلد، قابل فهم و همراه اقدام بعدی باشد. ورودی کاربر هنگام خطا حفظ شود.
- عملیات حساس با اقدام صریح و تأیید مناسب انجام شود؛ صرف انتخاب گزینه عملیات را نهایی نکند. CSRF، escaping و کنترل مجوز سرور حفظ شوند.
- راهنمای مشترک با `.help` و `data-help` به `#help-dialog` متصل است. سامانه tooltip موازی ساخته نشود. متن شامل هدف، داده، قاعده، نتیجه و محدودیت باشد؛ آستانه متغیر از تنظیمات واقعی تولید شود.
- هنگام بازشدن dialog، فوکوس داخل آن و پس از بسته‌شدن روی کنترل آغازگر بررسی شود. راهنما نباید از viewport بیرون بزند یا زیر والد بریده شود.
- هیچ تغییر ظاهری مجوز کاهش CSP یا افزودن handler درون‌خطی نیست. برای نمودار از الگوهای SVG و اسکریپت خارجی موجود استفاده شود.

## داده و نمودار

کارت و نمودار باید واحد شمارش، منبع و دامنه فیلتر مشخص داشته باشند. مسیر کلیک به رکوردها همین دامنه را حفظ کند. برای نمودار معادل متنی یا فهرست برچسب‌دار و مسیر قابل استفاده با صفحه‌کلید وجود داشته باشد. رنگ به تنهایی معنی را منتقل نکند.

«دریافت نشده»، «دریافت موفق بدون رکورد»، «پوشش ناقص یادداشت»، «صفر واقعی» و «نامشخص» یکسان نیستند. زمان آخرین دریافت موفق با تازه‌کردن مرورگر یا دریافت تک‌ردیفی جلو نرود. Issue با Backlog و اقدام محلی یکی نیست. CRM Done اثبات رفع نزد مشتری نیست؛ سن کیس زمان واقعی کار نیست. رنگ یا نمودار نباید رتبه‌بندی کارکنان یا قاعده تجاری جدید بسازد. قواعد از [معیارهای ذخیره‌شده](criteria.md) می‌آیند.

برای تغییر نمودار، [محیط تصویری](visual-workspace.md) و برای ابزارک‌ها [داشبوردهای شخصی](personal-dashboards.md) خوانده شوند. چیدمان ذخیره‌شده، گزینه‌های مجاز، مالکیت و انتشار مشترک در تغییر ظاهر حفظ شوند.

## ماتریس پذیرش تغییرات رابط

### جدول‌ها و انتخاب نمودار

- مشتری، عنوان، وضعیت و تاریخ‌های مرتبط ستون‌های مستقل داشته باشند؛ داده‌ها در سلول عنوان انباشته نشوند.
- ردیف‌ها فشرده و هم‌ارتفاع؛ متن بلند کوتاه‌نمایی شود و متن کامل با صفحه‌کلید یا جزئیات در دسترس بماند. عرض، ترتیب و نمایش ستون‌ها با کلید پایدار ذخیره شوند.
- مرتب‌سازی کل مجموعه پیش از صفحه‌بندی انجام شود؛ مرتب‌سازی صرفاً همان صفحه نباید به نام کل مجموعه معرفی شود. فیلتر مشتری/ماه در صفحه‌بندی و drill-down حفظ شود.
- مقایسه دسته‌ها: میله‌ای، ترجیحاً افقی برای نام بلند. سهم از کل: حلقه‌ای/دایره‌ای برای دسته‌های محدود. روند: خطی/ناحیه‌ای فقط با سابقه زمانی معتبر. انباشته: اجزای سازگار یک کل با واحد یکسان.
- کارت بدون سابقه واقعی sparkline ساختگی نداشته باشد. ابزارک کوچک مسیر نمایش کامل داشته باشد؛ کوچک‌کردن قلم جای طراحی واکنش‌گرا را نمی‌گیرد.
- نمودار و فهرست از مجموعه مبنای یکسان استفاده کنند؛ جمع دسته‌ها با احتساب نامشخص با آن تطبیق کند.

### ادغام راهنماها

در ۲۰۲۶-۱۰-۲۸ خروجی گفتگوی «Continuing from مهارت‌های طراحی گرافیکی Codex: Help the use…» با پروژه تطبیق داده شد. سه مهارت `service-*` و سند اولیه موجود حفظ و پنج مهارت تخصصی درخواستی اضافه شدند. مرجع مشترک همه آن‌ها همین سند است. این ادغام تصمیم‌ها و فایل‌های پروژه است؛ تاریخچه دو چت در رابط Codex ادغام فیزیکی نشده است.

این مرحله صرفاً زیرساخت طراحی است؛ هیچ صفحه، کتابخانه، API، منطق تجاری، داده یا نسخه عملیاتی تغییر نمی‌کند. انتخاب مهارت در [راهنمای پروژه](codex-project-guide.md) آمده است.

این موارد معیار بررسی‌اند، نه ادعای اینکه همگی اکنون پاس شده‌اند.

| سناریو | انتظار |
|---|---|
| عرض ۱۴۴۰، ۷۶۸ و ۳۶۰ پیکسل؛ روشن و تاریک | عنوان، اقدام، فیلتر و راهنما قابل استفاده؛ سرریز کل سند وجود نداشته باشد؛ جدول می‌تواند ناحیه اسکرول مستقل داشته باشد |
| بزرگ‌نمایی ۲۰۰٪ و برچسب بلند فارسی/شناسه لاتین | اطلاعات و کنترل ضروری پنهان یا روی هم نیفتند |
| Tab، Shift+Tab، Enter، Space، Escape | ترتیب منطقی، فوکوس آشکار، خروج و بازگشت درست dialog و عدم تله ناخواسته |
| loading / disabled | وضعیت قابل فهم، جلوگیری از ارسال تکراری و حفظ محتوای مفید قبلی |
| empty / unknown / partial | علت و اقدام بعدی مشخص؛ داده ناقص به صفر یا شکست کارمند تبدیل نشود |
| error / success | بازخورد نزدیک عمل و اعلان مناسب با `aria-live`؛ خطا اطلاعات واردشده را حذف نکند |
| confirmation / no access | تأیید مطابق عمل؛ منع سمت سرور مستقل از ظاهر دکمه |
| نمودار و گرید | فیلتر و شمارش و drill-down سازگار؛ تنظیمات کاربر حفظ شود |
| حرکت و کنتراست | کاهش حرکت رعایت شود؛ کنتراست متن، کنترل و فوکوس در هر دو تم اندازه‌گیری و نتیجه ثبت شود |

WCAG 2.2 AA هدف الزامات است؛ بررسی کامل صفحه‌خوان، کنتراست و همه مسیرهای کاربری باید شواهد مستقل داشته باشد. آزمون رندر به معنی قبولی این موارد نیست.

## اجرای امن و بررسی خودکار

پیش‌نمایش تعاملی فقط در محیط توسعه مستقل طبق [راهنمای اجرا](development-runtime.md) انجام شود. ابتدا وجود اجرای توسعه بررسی شود؛ سرور موازی روی همان پورت اجرا نشود. نسخه ثابت، وظیفه شبکه و `private/releases` برای طراحی تغییر نکنند. آزمون خودکار از fixture ساختگی و پایگاه تست Django استفاده کند، نه کپی اطلاعات کاری.

نمونه PowerShell از ریشه پروژه، در فرایند آزمایش مستقل:

```powershell
$env:SERVICE_SECRET_KEY = 'synthetic-test-only-not-for-deployment'
$env:SERVICE_ENVIRONMENT = 'development'
$env:SERVICE_DATABASE_PATH = Join-Path $env:TEMP 'service-ui-check.sqlite3'
.venv\Scripts\python.exe manage.py check
.venv\Scripts\python.exe manage.py test planning.test_presentation planning.test_visual_workspace --noinput
```

متغیرهای نمونه فقط برای فرایند آزمایش‌اند؛ به تنظیمات اجرای اصلی منتقل نشوند. دستور test دیتابیس تست مجزا می‌سازد. این مسیر فایل نمونه برای اجرای سرور یا migration نیست.

بر حسب تغییر، آزمون‌های `planning.test_visual_charts`، `planning.test_grid_preferences` و `planning.test_dashboards` اضافه شوند. برای تغییر تاریخ، مجوز یا معیار، آزمون همان ماژول نیز اجرا شود. وابستگی و build تازه برای تغییر صرفاً مستندات لازم نیست. گزارش شامل دستور، تعداد/نتیجه واقعی و موارد اجرا‌نشده باشد. تغییر رفتار همراه راهنمای قابلیت و تاریخچه افزایشی ثبت شود؛ این سند جای تاریخچه انتشار نیست.
