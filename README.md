# ServiceManagementApp

دستیار مدیریتی خدمات پس از فروش برای مشاهده وضعیت، تصمیم‌گیری مستند و پیگیری بهبود خدمات از استقرار تا پشتیبانی.

**نسخه فعلی: `0.6.28` — به‌روزرسانی مستندات: ۴ آبان ۱۴۰۵ (۲۰۲۶-۱۰-۲۶).**

این محصول مستقل از MyBarid-AI است. تمرکز آن داشبوردهای مدیریتی و رسیدن از نمودار به رکورد و اقدام است؛ نه رتبه‌بندی خودکار کارکنان. CRM فقط خوانده می‌شود و اقدام‌ها و تصمیم‌های محلی در پایگاه داده برنامه ذخیره می‌شوند.

برای شناخت کامل یا تحویل به مدل AI، از [سند یکپارچه محصول و معماری](docs/AI-HANDOVER.md) شروع کنید. این README وضعیت جاری را توضیح می‌دهد؛ اسناد طراحی اولیه و بخش‌های نسخه‌دار سایر اسناد ممکن است تاریخی باشند.

نسخه ۰.۶.۲۸ در نصب فعلی روی محیط اصلی و شبکه فعال شده است. محصول همچنان پایلوت داخلی محدود برای حدود ۳ تا ۴ کاربر است، نه استقرار نهایی سازمانی.

### اصلاح بازدید دوره‌ای در ۰.۶.۲۸

داشبورد اکنون منبع مستقلی از بکلاگ عمومی دارد. عضویت از View انتخابی تعیین می‌شود؛ خالی‌بودن Case Service موجب حذف بازدید نمی‌شود. فیلتر ماه، شهر و جست‌وجو پیش از محاسبه کارت‌ها، نمودارها و گرید اعمال می‌شوند.

View پیش‌فرض این بخش «همه بکلاگ های بازدید دوره ای جاری خدمات عمومی» است و انتخاب ذخیره‌شده کاربر حفظ می‌شود. گزارش جاری با عملکرد کامل ماه متفاوت است: برای نمایش انجام‌شده و باقی‌مانده، View باید پایان‌یافته‌ها را نیز شامل شود و معیارهای وضعیت معتبر باشند. جزئیات: [گزارش تطبیق و پذیرش](docs/periodic-reconciliation.md).

## استفاده روزمره در نصب فعلی

| محیط | نشانی | منبع کد و داده |
|---|---|---|
| اصلی روی میزبان | http://127.0.0.1:8769/ | انتشار ثابت، دیتابیس کاری |
| شبکه داخلی | http://172.16.5.18:8766/ | انتشار ثابت، همان دیتابیس کاری |
| توسعه | http://127.0.0.1:8768/ | کد در حال توسعه، دیتابیس مستقل |

نشانی شبکه مربوط به نصب فعلی است و با تغییر IP میزبان باید تنظیم شود. `127.0.0.1` روی رایانه همکار به همان رایانه اشاره می‌کند؛ همکاران از نشانی شبکه و حساب اختصاصی استفاده می‌کنند. نصب برنامه یا کپی دیتابیس روی رایانه همکار لازم نیست.

سه وظیفه ویندوز `ServiceManagementApp-stable`، `ServiceManagementApp-network` و `ServiceManagementApp-development` اجراها را مدیریت می‌کنند. هنگامی که این وظیفه‌ها فعال‌اند، سرور دیگری روی همان پورت اجرا نکنید. اجرای برنامه وابسته به بازبودن Codex یا مرورگر نیست؛ اما میزبان باید روشن و بیدار باشد. اجرای فعلی به نشست ویندوز وابسته است و سرویس تضمین‌شده پیش از ورود کاربر نیست.

۱. وارد زیرسیستم موردنظر شوید.
۲. در تنظیمات همان ماژول، View اصلی و View یادداشت را انتخاب و ذخیره کنید.
۳. دکمه دریافت بالای صفحه را بزنید و نتیجه عملیات را بررسی کنید.
۴. از نمودار به فهرست رکوردها بروید و اقدام محلی ثبت یا پیگیری کنید.

تازه‌کردن مرورگر، دریافت CRM نیست. زمان آخرین موفقیت و پوشش یادداشت جدا نمایش داده می‌شوند؛ پس از ۲۴ ساعت از آخرین دریافت موفق هشدار داده می‌شود. دریافت تکی، زمان دریافت کامل View را جلو نمی‌برد.

## نصب و اجرای توسعه روی ویندوز

محیط بررسی‌شده Python 3.14 است؛ وابستگی‌ها در `requirements.txt` ثبت شده‌اند. در پوشه پروژه:

```powershell
python -m venv .venv
python -m pip --python .venv\Scripts\python.exe install -r requirements.txt
.venv\Scripts\python.exe runtime.py development
```

این دستور توسعه را روی پورت 8768 با `private/development.sqlite3` اجرا می‌کند. اگر وظیفه توسعه از قبل فعال است، اجرای دستی موازی لازم نیست. اجرای مدیریت‌شده برای دریافت تغییر کد به راه‌اندازی مجدد همان وظیفه توسعه نیاز دارد؛ نسخه اصلی را برای آزمایش متوقف نکنید.

کپی اولیه دیتابیس کاری به توسعه، فقط در صورت نیاز و نبود دیتابیس توسعه:

```powershell
.venv\Scripts\python.exe runtime.py development --copy-current
```

این گزینه دیتابیس توسعه موجود را بازنویسی نمی‌کند. کپی ایجادشده حاوی داده محرمانه است؛ برای آزمون خودکار از داده ساختگی استفاده شود.

`run_preview.py` و پورت 8765 مسیر قدیمی اجرای نمونه‌اند؛ راهنمای اجرای روزمره نصب فعلی نیستند. اجرای محلی بدون رمز را هرگز در شبکه منتشر نکنید.

## انتشار و جداسازی محیط‌ها

آماده‌سازی انتشار مستقل:

```powershell
.venv\Scripts\python.exe runtime.py prepare
```

این دستور کد، فایل‌های رابط و مستندات را در پوشه جدید `private/releases/` کپی می‌کند؛ **نسخه در حال اجرای وظیفه‌های ویندوز را فعال یا تعویض نمی‌کند**. انتشارهای موجود مستقیم ویرایش نشوند.

برای فعال‌سازی: آزمون‌های مرتبط، بررسی نبود دریافت فعال، پشتیبان سازگار SQLite، اعمال migrationهای لازم، سپس تغییر هماهنگ منبع اجرای اصلی و شبکه و کنترل سلامت لازم است. برای ۰.۶.۲۸ migration شماره `integrations.0010` لازم بود. دیتابیس توسعه نباید جایگزین داده کاری شود. انتشار بدون توقف تضمین نشده است.

دستورهای `runtime.py stable` و `runtime.py stable --network` برای اجرای دستی انتشار آماده‌شده‌اند؛ در نصب دارای وظیفه فعال، آن‌ها را هم‌زمان اجرا نکنید. راهنمای دقیق و سوابق انتشار: [اجرای پایدار و توسعه](docs/development-runtime.md).

## معماری و داده

- برنامه ماژولار Django با قالب سمت سرور، JavaScript و دارایی‌های محلی؛ Waitress برای شبکه.
- SQLite روی دیسک میزبان؛ مرورگرها به برنامه وصل می‌شوند، نه مستقیم به دیتابیس.
- منبع عملیاتی `private/preview.sqlite3` و منبع توسعه `private/development.sqlite3` است.
- دریافت CRM با هویت ویندوز اجراکننده میزبان انجام می‌شود؛ نقش برنامه معادل هویت مستقل CRM نیست.
- `scope` اتصال و انتخاب View، دامنه داده را مشخص می‌کنند. snapshot و وضعیت دریافت ماژول‌ها مستقل‌اند.
- زمان‌بند فقط در اجرای اصلی stable فعال است؛ خاموش‌کردن تنظیم عمومی دریافت خودکار، همه زمان‌بندی‌ها را متوقف می‌کند.
- تصمیم‌ها و پیگیری‌های محلی هنگام بازخوانی CRM حفظ می‌شوند.

| پوشه | مسئولیت |
|---|---|
| `config/` | تنظیمات اجرا، دسترسی، کاربران، پشتیبان و ترجیحات گرید |
| `integrations/` | ارتباط CRM، نرمال‌سازی، snapshot، صف و زمان‌بندی دریافت |
| `criteria/` | معیارهای ذخیره‌شده و ارزیابی قابل توضیح |
| `planning/` | برنامه‌ریزی، بکلاگ، ارتقا، بازدید و نمودارها |
| `projects/` | دریافت و نمایش پروژه‌ها |
| `templates/` و `static/` | رابط فارسی، نمودار، گرید و راهنما |
| `docs/` | قراردادها، راهنماها، محدودیت‌ها و گزارش پذیرش |
| `private/` | داده و تنظیمات عملیاتی و انتشار و پشتیبان؛ خارج از Git |

## قواعد تفسیر و محدودیت‌های فعلی

- Issue مسئله مشتری و Backlog برنامه اجرای خدمت است؛ چند Issue می‌توانند به یک Backlog وصل شوند.
- تعداد کیس مرتبط با اقدام، تعداد قطعی قابل بستن نیست. شمارش رفع بر اساس Done/Goal Version فعلاً فعال نیست.
- CRM Done معادل تأیید رفع نزد مشتری نیست؛ Release ماه برنامه است، نه تاریخ واقعی انجام.
- زمان از ایجاد کیس، زمان واقعی کار کارشناس یا مدت ماندگاری در هر وضعیت نیست.
- نمودار ایجاد ماهانه از رکوردهای مجموعه فعلی ساخته می‌شود؛ تاریخچه حجم کار گذشته را بازسازی نمی‌کند.
- یادداشت‌ها تنها در محدوده View یادداشت انتخابی و دسترسی اتصال دریافت می‌شوند.
- داده نامشخص یا دریافت‌نشده نباید صفر یا کم‌کاری کارشناس تلقی شود.
- نقش‌های فعلی مشاهده‌گر، کارشناس و مدیر هستند؛ همه اعضای مجاز پایلوت محیط مشترک را می‌بینند. دسترسی تیمی/فردی هنوز پیاده نشده است.
- HTTPS، PostgreSQL، سرویس مستقل از ورود ویندوز و آزمون کامل بار و بازیابی سازمانی هنوز تکمیل نشده‌اند. محیط فعلی برای اینترنت عمومی نیست.
- تنظیمات AI موجود است، اما تحلیل AI عملیاتی و اتصال تلفن قابلیت تکمیل‌شده نیستند.
- ورود اکسل و مقایسه دو دوره در محدوده جاری محصول نیستند.
- ادعای انطباق کامل WCAG یا ASVS وجود ندارد.

## پشتیبان و محرمانگی

فرم `/settings/backups/` فقط **تنظیمات** اتصال، View، ماژول و معیارها را پشتیبان می‌گیرد؛ کاربران، کیس‌ها، یادداشت‌ها و اقدام‌های محلی در آن نیستند. فایل امضاشده است، نه رمزگذاری‌شده. بازیابی به کلید همین نصب وابسته است و رکوردهای جدیدترِ خارج فایل را حذف نمی‌کند. [راهنمای پشتیبان و کاربران](docs/account-backup-tools.md).

پشتیبان کامل کسب‌وکار باید جدا تهیه و بازیابی آن آزمایش شود. در حالت WAL، کپی صرف فایل اصلی SQLite هنگام اجرا کافی نیست؛ از API پشتیبان SQLite یا روش توقف و checkpoint معتبر استفاده کنید.

مخزن عمومی است: داده مشتری و کارکنان، خروجی CRM، رمز، توکن، کلید، پشتیبان و فایل‌های خصوصی وارد Git نشوند. تست‌ها از نمونه ساختگی استفاده کنند. `gitignore` جای بررسی محتویات پیش از انتشار نیست.
